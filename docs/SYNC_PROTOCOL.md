# Sync Protocol

**Presence split:** Web = chat UI; Flutter = Field Body (bridge/tools/confirm); Windows = agent. See [dev/PRESENCE_STACKS.md](dev/PRESENCE_STACKS.md) · [dev/SYNC_PLAN.md](dev/SYNC_PLAN.md).

## Architecture

Brain is source of truth. Clients are edges. All mutations go through brain.

```text
Client ──REST/WS──► Brain (SQLite SoT)
                    ↕ push
Client ◄──WS push── Brain
```

## Entities synced

| Entity | Key | Conflict strategy |
|--------|-----|-------------------|
| memories | `(user_id, key)` | Last-write-wins (v1) |
| habits | `(pattern_type, pattern_key)` | Brain-authoritative |
| sessions | `(session_id)` | Append-only messages |
| preferences | `(user_id, key)` | Last-write-wins |
| action_log | `(id)` | Append-only, never update |

## WebSocket — /ws

Connections must be authenticated using the `device_token`. This can be provided as a query parameter (`?token=...`) or included in the first JSON payload sent to the socket (`{"token": "..."}`). Unauthenticated connections are rejected in production.

Messages are JSON with `type` field:

```json
// Client → Brain
{"type": "message", "session_id": "...", "text": "...", "device_id": "..."}
{"type": "ping"}
{"type": "register", "device_id": "...", "token": "..."}     // bind connection and optionally authenticate
{"type": "tool_result", "request_id": "...", "status": "ok", "result": {...}}  // bridge response

// Brain → Client  
{"type": "chunk", "session_id": "...", "text": "..."}
{"type": "done", "session_id": "...", "tool_calls": [...]}
{"type": "confirm_request", "tool": "...", "params": {...}, "request_id": "..."}  // Brain blocking on confirmation
{"type": "push_memory", "key": "...", "value": "..."}
{"type": "pong"}
{"type": "registered", "device_id": "..."}                   // ack to register
{"type": "tool_execute", "request_id": "...", "session_id": "...", "tool": "...", "params": {...}}  // bridge request
```

### Confirmation Flow
When the brain blocks a tool requiring confirmation, it sends `confirm_request` to the active device.
To **approve** the request, the client must send a standard text message with the confirmation phrase (e.g. `{"type": "message", "text": "confirm", "session_id": "..."}`).
To **deny** the request, the client can simply do nothing, or send a text message cancelling it. The text message route ensures full compatibility with the existing web chat UI.

## Device bridge (Phase 2 — ISSUE-032 Windows, ISSUE-033 Android)

Client-executor tools (`executor: "client"`) are dispatched by the brain to a
specific device over the WebSocket using a request/response correlation:

1. Client connects to `/ws` and sends `{"type": "register", "device_id": "..."}`.
2. Brain acks with `{"type": "registered", "device_id": "..."}` and routes
   client-executor tools to that device.
3. When the Mind calls a client tool (e.g. `windows_open` / `android_open`),
   the brain sends
   `{"type": "tool_execute", "request_id": "...", "tool": "...", "params": {...}}`
   to the target device and waits (default 30s).
4. The client executes the local action and replies with
   `{"type": "tool_result", "request_id": "...", "status": "ok|error", "result": {...}}`.
5. The brain completes the pending request, returns the result to the Mind
   loop, and writes it to `action_log` (audit).

The `request_id` is a UUID generated by the brain; the client must echo it back
so the brain can correlate the response. If the device is offline or times out,
the tool returns an error dict.

### Client tools

| Tool | Params | Behaviour |
|------|--------|-----------|
| `windows_open` | `target`: URL \| absolute file/path \| app name | Windows: opens with the OS default handler (browser / explorer / `start`) |
| `android_open` | `target`: URL (`https://` / `market://`) \| app package name | Android: `ACTION_VIEW` intent / launch package, e.g. `com.google.android.youtube` |

## Device pairing

1. Client shows pairing code (6-digit derived from `JARVIS_PAIRING_SECRET`)
2. Brain verifies code, issues `device_token` (JWT, 30-day expiry)
3. All subsequent requests use `Authorization: Bearer {device_token}`

## Conflict resolution (v1)

Last-write-wins using `updated_at` timestamp (implemented in `upsert_memory`;
a stale write is rejected and returns `applied: false`). A client with a
fresher copy can pass its own `updated_at` to `PUT /soul/memories/{key}` so
the brain converges to the newest write. A `push_memory` with an empty `value`
signals a deletion to clients. v2 will use CRDTs for memory (see SCOPE.md).

### Client-side mirror (ISSUE-022)

The Windows client keeps a best-effort local mirror of memories at
`~/.jarvis/windows_sync_cache.json`, updated in near-real-time as the brain
broadcasts `push_memory`. The brain remains the source of truth; this cache
just makes a memory written on one device visible on another immediately.

## Offline behaviour

- Client queues messages locally while brain unreachable
- On reconnect, flush queue in order
- Brain deduplicates by `message_id` (UUID per message)
